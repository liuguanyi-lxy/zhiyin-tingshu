# 知音听书后端项目代码阅读指南

这份文档用于帮助第一次阅读本项目的人建立“请求从哪里进来、经过哪些模块、数据最后落到哪里”的整体认识。源码中的注释重点解释设计意图和调用关系，而不是重复 Java 语法。

## 1. 先建立整体模型

项目是一个 Maven 多模块的 Spring Cloud 微服务工程。前端请求通常不会直接访问业务服务，而是先进入网关：

    微信小程序 / 管理后台
            |
            v
    server-gateway:8500
            |
            +--> service-album:8501      专辑、声音、分类、文件上传
            +--> service-search:8502     Elasticsearch 搜索、联想、排行
            +--> service-user:8503       微信登录、用户、VIP、购买记录
            +--> service-order:8504      交易、订单、订单超时取消
            +--> service-account:8505    账户余额、充值
            +--> service-payment:8506    微信支付、支付回调
            +--> service-live:8507       直播
            +--> service-comment:8508    MongoDB 评论
            +--> service-dispatch:8509   XXL-JOB 定时任务

`service-client` 不是真正提供业务数据的服务，而是集中存放 OpenFeign 接口。一个服务需要调用另一个服务时，通常依赖对应的 client 模块，通过 Feign 完成远程调用。

## 2. Maven 模块职责

| 模块 | 主要职责 | 阅读重点 |
|---|---|---|
| `common/common-util` | `Result`、错误码、用户上下文、通用工具 | 所有服务都会依赖 |
| `common/service-util` | 登录切面、缓存切面、异常处理、MyBatis-Plus 和 Redis 配置 | 跨服务共用的运行机制 |
| `common/rabbit-util` | RabbitMQ 发送、消息确认和 MQ 常量 | 异步解耦与最终一致性 |
| `common/common-log` | 操作日志注解和 AOP | 管理端操作日志 |
| `model` | 数据库实体、查询对象、视图对象、ES 文档对象 | 服务之间传递的数据结构 |
| `service/*` | 各业务微服务的 Controller、Service、Mapper、Receiver | 具体业务实现 |
| `service-client/*` | Feign 接口及降级实现 | 服务间调用边界 |
| `server-gateway` | 路由、CORS、全局鉴权、WebSocket 转发 | 所有外部请求的入口 |

## 3. 一次 HTTP 请求的完整路径

以“查询专辑详情”为例，建议按以下顺序阅读：

1. `server-gateway` 的 Nacos 路由配置根据 `/api/album/**` 或 `/api/search/**` 选择目标服务。
2. `AuthGlobalFilter` 在网关层检查路径是否白名单；非白名单请求必须携带 `token`，并且 Redis 中存在这个 token。
3. 目标服务的 `api/*ApiController` 接收参数，并把 HTTP 参数转换成业务对象。
4. 如果接口加了 `@LoginVerification`，`LoginAspect` 会再次检查登录状态，并把用户 ID 写入 `AuthContextHolder`。
5. Controller 调用 `service` 接口；`service/impl` 负责业务编排。
6. 本服务自己的数据通过 MyBatis-Plus `Mapper` 访问 MySQL；其他服务的数据通过 `service-client` 中的 Feign 接口获取。
7. 查询类方法可能通过 `@RedisCache` 进入 `RedisCacheAspect`，执行“查缓存、加锁回源、回填缓存”的流程。
8. 修改类操作如果会影响搜索、统计或其他服务，通常通过 `RabbitService` 发送 MQ 消息，而不是同步调用所有后续动作。
9. 返回值统一封装为 `Result<T>`，异常由 `GlobalExceptionHandler` 转成同样的响应格式。

## 4. 两层登录校验

项目同时存在网关鉴权和服务鉴权，两者职责不同。

### 4.1 网关层：拦截未登录请求

`server-gateway/.../AuthGlobalFilter.java`：

- 白名单路径直接放行，例如微信登录、支付回调、公开搜索和专辑详情。
- 其他路径读取请求头 `token`。
- Redis 的 key 是裸 token，不是 `user:login:` 加 token。
- token 不存在时返回 HTTP 200，但业务码为 `208`，因为前端会根据 `statusCode == 200 && code == 208` 触发重新登录。

### 4.2 服务层：校验注解并建立用户上下文

`common/service-util/.../LoginAspect.java`：

- 切点只拦截 `*.api.*` 包中带 `@LoginVerification` 的方法。
- `required=true` 表示必须登录；`required=false` 表示允许匿名访问，但如果请求带有效 token，仍会把用户 ID 写入上下文。
- 调用业务方法前写入 `AuthContextHolder`。
- 调用结束后必须清理 ThreadLocal，避免 Tomcat 线程复用造成用户串号或越权。

因此，业务代码中看到 `AuthContextHolder.getUserId()` 时，要向上追溯该接口是否加了 `@LoginVerification`。

## 5. 统一响应和异常

### 5.1 `Result<T>`

所有 API 默认返回 `Result<T>`：

- `code`：业务状态码，成功一般是 `200`。
- `message`：前端可展示或用于调试的消息。
- `data`：真正的业务数据，可以是对象、列表、分页对象或空值。

错误码集中在 `common/common-util/.../ResultCodeEnum.java`。登录过期是 `208`，参数校验错误是 `206`，余额不足是 `219`。

### 5.2 `GlobalExceptionHandler`

业务代码不要为了返回错误结果到处写重复判断。遇到明确的业务错误时抛出 `GuiguException`，全局异常处理器会保留错误码和消息；参数校验异常则被转换为字段到错误信息的 Map。

## 6. Redis 缓存流程

`RedisCacheAspect` 对标记 `@RedisCache` 的方法进行增强：

    请求方法
      |
      +--> 拼接 prefix + 参数得到 key
      |
      +--> Redis 命中：直接返回
      |
      +--> 未命中：竞争 key 对应的 Redisson 分布式锁
                  |
                  +--> 没抢到锁：短暂等待，再查缓存
                  +--> 抢到锁：二次查缓存
                                  |
                                  +--> 仍未命中：执行原方法查库
                                                  |
                                                  +--> 非空：写入带随机抖动的 TTL
                                                  +--> 空值：写入短 TTL 占位值

这里的三个防护点：防穿透（数据库查不到时缓存空值）、防击穿（同一个 key 只允许一个线程回源）、防雪崩（缓存过期时间加入随机抖动）。

专辑详情还额外使用 Redisson 布隆过滤器。布隆过滤器判断“不存在”时可以直接拒绝明显不存在的专辑 ID，但判断“存在”并不代表数据库一定存在，所以仍然要继续查缓存或数据库。

## 7. Feign 调用和降级

跨服务调用不要直接拼 URL，而是：

1. 在 `service-client` 中查找或定义 `@FeignClient` 接口。
2. 为接口配置对应的 `*DegradeFeignClient` 降级实现。
3. 在业务服务中注入 Feign 接口并调用。
4. `FeignInterceptor` 自动透传上游的 `token` 和 `traceId`。

Feign 调用要区分两种失败：业务返回失败，以及远程服务不可用触发 fallback。阅读 Feign 调用时，应同时打开调用方 ServiceImpl、Feign 接口和被调用方 ApiController。

## 8. RabbitMQ 消息流程

发送端通常调用 `rabbitService.sendMessage(exchange, routingKey, message)` 或 `sendDealyMessage(...)`。`MqConst` 集中保存交换机、路由键和队列名称。

消费端使用 `@RabbitListener` 声明绑定，并采用手动确认：解析消息、执行幂等检查、调用业务 Service、业务成功后调用 `channel.basicAck(...)`。消费线程结束时要清理 trace 上下文。

消息幂等常见做法是使用业务编号调用 Redis `setIfAbsent`，第一次消费成功设置标记，重复消息因为 key 已存在而不再重复执行业务。

## 9. 订单和支付主链路

    trade
      -> 根据 VIP / 专辑 / 声音计算原价、优惠和订单明细
      -> Redis 保存 tradeNo，防止重复提交
      -> 对订单明细签名，防止前端篡改金额

    submitOrder
      -> 校验签名和 tradeNo
      -> 创建订单、订单明细、优惠明细
      -> 锁定账户余额或创建微信支付预支付单
      -> 发送订单超时取消延迟消息

    支付成功
      -> payment 服务接收微信回调
      -> 发送支付成功 MQ 消息
      -> order 服务更新订单状态
      -> user 服务写入购买记录
      -> account 服务完成余额扣减或解锁

阅读订单代码时，重点关注重复提交如何拦截、订单金额如何防篡改、异常时账户锁定如何释放。涉及多个数据库的写操作时，留意 `@GlobalTransactional` 的边界。

## 10. 搜索和数据同步

`service-search` 是项目中直接操作 Elasticsearch 的服务。专辑 MySQL 数据发生变化后，通常通过 MQ 通知搜索服务：专辑上架写入或更新 ES，专辑下架删除或标记不可搜索，统计变更同步索引字段。

`service-cdc` 通过 Canal 监听 MySQL binlog，用于删除或更新 Redis 缓存。这样数据库修改不必依赖所有写入口都主动记得清缓存。

## 11. 推荐阅读顺序

第一遍只看骨架：根目录 `pom.xml`、网关启动类和 `AuthGlobalFilter`、`Result`/错误码/`AuthContextHolder`、任意服务的 `*Application`/`api`/`service`/`mapper`。

第二遍看横切机制：`LoginAspect`、`RedisCacheAspect`、`FeignInterceptor`、`RabbitService`/`MqConst`/一个 `receiver`、`GlobalExceptionHandler`。

第三遍选一条业务链路，推荐“专辑详情”或“订单支付”。每读一个 Controller 方法，都继续追到 Service、Mapper/Feign、MQ Receiver，直到找到数据最终写入的位置。

## 12. 调试排查清单

- 请求是否进入网关，路由前缀是否正确。
- 是否被 `AuthGlobalFilter` 以 `208` 拦截。
- 服务接口是否加了正确的 `@LoginVerification`。
- `AuthContextHolder.getUserId()` 是否为 null。
- Feign 是否透传了 `token`，对端是否命中了正确的 API 路径。
- 缓存 key、Redis 数据类型和 TTL 是否符合预期。
- MQ 的 exchange、routing key、queue 是否来自同一组 `MqConst` 常量。
- 消费者是否执行了 `basicAck`，幂等 key 是否已经存在。
- 订单问题优先检查 tradeNo、签名、订单状态和账户锁定状态。
- 使用 `traceId` 串联网关、服务、Feign 和 MQ 消费日志。
