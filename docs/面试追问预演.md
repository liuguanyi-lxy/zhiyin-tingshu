# 面试追问预演 —— 知音听书项目问答手册

> 所有答案均锚定仓库真实代码，每条给出：面试官的追问链 → 回答要点 → 对应代码位置。
> 使用方法：先自己口头答一遍，再对照要点，答不出的回到代码里重读那一段。

## 一、面试官问项目的一般套路

1. **总览题**（2-3 分钟）："介绍一下你这个项目" / "架构是怎样的、为什么这么拆"
2. **深挖题**（主体，10-20 分钟）：从简历里挑一条，沿着"是什么 → 为什么这么做 → 有什么问题 → 怎么解决"追 3-4 层
3. **场景变式**："并发量翻十倍怎么办" / "Redis 挂了会怎样" / "这条消息丢了怎么办"
4. **压力/对比题**："这个技术为什么不用 XXX" / "这个数字怎么测出来的"
5. **收尾**："项目里你最有成就感的点" / "让你重来一次会改什么"

回答总原则：**结论先行 → 讲清楚"为什么选这个方案" → 主动暴露取舍和踩过的坑**。
背课件的候选人只答"是什么"，你要靠"为什么 + 取舍"拉开差距。

## 二、项目介绍话术

### 1 分钟版（自我介绍后被点名"讲讲项目"）

> 知音听书是一个微信小程序听书平台，后端是 Spring Cloud Alibaba 微服务，拆了用户、专辑、搜索、
> 订单、支付、账户等 9 个服务，网关统一鉴权。核心链路有三条：微信登录鉴权、基于 ES 的内容搜索、
> 以及余额+微信支付双通道的交易链路。我负责整个后端从 0 到 1 的搭建和两轮生产级加固：
> 一轮是性能（ES 替换 MySQL 模糊查询、CompletableFuture 并行聚合），一轮是资金安全
> （支付回调验签、金额校验、三处状态机幂等），并且给核心链路补了 28 个单元测试。

### 3 分钟版（追问"详细讲讲"）

在 1 分钟版基础上展开三条链路各自的难点（登录双层防护、缓存三大问题、支付幂等），
每条控制在 40 秒，讲完主动停下来："这三块您对哪块感兴趣可以展开。"
——**把提问权交给面试官，避免被动的长篇大论。**

## 三、登录鉴权（简历第 1 条）

**追问链：token 放 Redis 为什么 → 网关和服务层为什么两层 → Feign 调用怎么带登录态 → 208 是什么约定**

1. **"为什么用 UUID token 存 Redis，而不是 JWT？"**
   要点：JWT 无状态但**无法主动失效**（登出/封号后 token 仍有效，除非再维护黑名单，
   那就又变成有状态）；本项目登录态需要服务端强控制（token 单点、可随时踢下线），
   Redis 校验 O(1)，成本可接受。
2. **"网关已经校验了，服务层为什么还要 @LoginVerification？"**
   要点：双层防护。网关挡外部流量，但**服务间 Feign 调用不走网关**，内部调用需要独立
   的用户上下文；同时防止将来某个服务被单独暴露端口时裸奔。网关管"能不能进来"，
   切面管"这个线程是谁"。
3. **"用户上下文怎么传递的？"**
   要点：网关把 token 对应的 userId 放进请求头 → 服务层 AOP（LoginAspect）解析后写入
   ThreadLocal（AuthContextHolder）→ 业务代码直接取；**Feign 拦截器把 userId 塞进
   请求头透传给下游**，否则下游解析不到（异步线程没有 RequestContextHolder，做了兜底）。
4. **"208 是什么？"**
   要点：与前端约定 HTTP 200 + body code=208 表示登录过期，前端统一在 request 封装里
   拦截 208 弹窗跳登录页，登录后跳回来源页。选择 200+208 而不是 401，是因为小程序
   request 的 fail 回调处理 401 体验差，统一在 success 里分流。

## 四、搜索（简历第 2 条）

**追问链：为什么快 → 三路补全怎么实现 → 数据怎么进 ES → 500ms→50ms 怎么测的**

1. **"ES 为什么比 MySQL LIKE 快？"**
   要点：LIKE '%xx%' 无法走 B+ 树索引，全表扫描；ES 用倒排索引，分词后按词项定位
   文档（O(词表) 级别）。这是结构性差异，不是调优差异。
2. **"中文、拼音、首字母三路补全怎么做的？"**
   要点：completion suggester + 自定义索引结构，同一字段做多路：主分词器 ik 处理中文，
   pinyin 分词器（first_letter 参数）处理拼音和首字母；写入时把三个维度的输入都灌进
   completion 字段。查询时一个 suggest 请求带三个上下文。
3. **"MySQL 数据怎么同步到 ES？"**
   要点：专辑上/下架时由 album 服务发 MQ，search 服务消费后写 ES（业务事件驱动，
   保证上/下架实时性），不是全量定时同步。
4. **"500ms→50ms 哪来的？"**
   要点：JMeter 对同一批关键词压测 MySQL LIKE 版和 ES 版取均值。**主动说明测试条件**
   （数据量 10 万级、关键词集合、预热情况），如果没做严格对照就直接说测试方法，
   别硬撑数字精确性。
5. **"详情页为什么要并行聚合？"**
   要点：详情页需要专辑信息+分类+主播+统计四个上游，串行 4 次网络往返；用
   CompletableFuture 并行调用，总耗时从"四次之和"降到"最慢的一个"。
   **主动承认踩过的坑**：四个线程往同一个 HashMap 写，是有并发 bug 的，已改
   ConcurrentHashMap 并加了聚合完整性测试。

## 五、缓存治理（简历第 3 条）

**追问链：穿透/击穿/雪崩分别怎么办 → 布隆过滤器原理 → 为什么删缓存不是更新缓存 → Canal 原理**

1. **"三大问题分别怎么处理的？"**
   要点（全部落在自定义 @RedisCache 注解 + AOP 里）：
   - 穿透：查不到也缓存空值占位（短 TTL 30s），恶意 id 不再反复打库
   - 击穿：热点 key 失效瞬间，用 Redisson 分布式锁（**key 级锁粒度**，不是全局一把锁）
     + 抢到锁后 Double Check；抢锁失败自旋重试 3 次，仍失败**降级直查 DB**保可用性
   - 雪崩：TTL = 基础 300s + 0~60s 随机抖动，避免同时失效
2. **"布隆过滤器为什么能防穿透？误判怎么办？"**
   要点：将合法 id 集合预先 load 进布隆过滤器，查询先过过滤器——**它说不存在就一定
   不存在**，直接返回；误判方向只有"存在但实际不存在"，这种会走到缓存空值兜底。
   不能删除元素，所以适合 id 集合相对稳定的场景。
3. **"Canal 原理？为什么删缓存而不是更新缓存？"**
   要点：Canal 伪装成 MySQL 从库拉 binlog，解析变更事件后删对应缓存 key。
   选择"删除"而非"更新缓存"：并发写时更新缓存的顺序不可控（后写的可能先到），
   删除是幂等的，下次读时回源重建，保证最终一致。
4. **"Canal 挂了缓存就一直脏，怎么办？"**
   要点：诚实答——当前实现 canal 侧删缓存是最终一致性的唯一手段，canal 挂掉期间
   会脏读，靠 canal 重连后追 binlog 恢复。可改进方向：缓存 TTL 兜底（已有 300s，
   最长脏 5 分钟）+ 关键写路径补主动删缓存。

## 六、MQ 与分布式事务（简历第 4 条）

**追问链：消息怎么不丢 → 怎么不重 → 延迟队列为什么用 Redisson → Seata AT 原理**

1. **"消息丢失的三个环节怎么保证？"**
   要点：生产端——publisher confirm + return 回调，失败重发（元数据暂存 Redis，重试上限 3 次）；
   broker 端——交换机/队列/消息都持久化；消费端——手动 basicAck，业务处理完才确认。
2. **"重发会不会导致重复消费？"**
   要点：会，所以消费端幂等：播放上报用 Redis setIfAbsent 做消费幂等键；
   支付链路用**数据库条件更新**（见支付一节）。
3. **"订单超时为什么用 Redisson 延迟队列而不是 RabbitMQ 死信队列？"**
   要点：自主选型。RabbitMQ 延迟消息（TTL+死信）有队头阻塞问题——前面有长延迟消息时
   后面短延迟的要排队；Redisson RDelayedQueue 按到期时间投递，且我们已引入 Redisson，
   不加新组件。代价：延迟数据在 Redis，需考虑持久化（面试可主动提这个 trade-off）。
4. **"Seata AT 模式原理？"**
   要点：一阶段——代理数据源，业务 SQL 执行时自动记录前后镜像到 undo_log 并注册分支事务；
   二阶段——全局提交则异步删 undo_log，回滚则按 before 镜像反向补偿。用在下单跨
   order/account/user 三库的链路。为什么不用 TCC：开发成本高，AT 对业务无侵入，
   我们的一致性窗口要求不高（秒级），AT 够用。

## 七、支付链路（简历第 6 条，最重的一条，必问）

**追问链：回调怎么验签 → 怎么防篡改 → 为什么条件更新能幂等 → 回调失败怎么办 → 轮询和回调并发怎么办 → 没真实商户号怎么验证的**

1. **"回调验签怎么做的？"**
   要点：微信支付 V3 回调带 Wechatpay-Signature 等签名头，用官方 SDK 的
   NotificationParser，以平台证书（通过自动更新证书机制获得）验签 + APIv3 密钥解密
   报文，时间戳校验防重放。验签失败直接返回 FAIL。
2. **"怎么防止金额篡改？"**
   要点：下单金额取自本地支付记录（元转分），回调报文的 total 与本地逐位比对，
   不一致记日志并抛异常返回 FAIL。防的是"1 分钱支付整单"这类攻击。
3. **"为什么数据库条件更新能实现幂等？"**
   要点：`UPDATE ... SET status=PAID WHERE order_no=? AND status=UNPAID`——
   这条 UPDATE 带 WHERE 状态前置判断，数据库行锁保证同一订单的多次更新**串行执行**：
   第一次更新 status 已变，后续更新的 WHERE 不再命中，受影响行数为 0。
   以"行数是否 > 0"作为"本请求是否是第一个处理者"的判定，只有第一个处理者发 MQ、
   发权益。这是把幂等判断下沉到数据库原子性里，比"先查状态再更新"（check-then-act，
   并发下两个请求都能通过检查）可靠。
4. **"回调失败微信会怎么样？"**
   要点：微信按衰减间隔重试（15s/15s/30s/3m/...，约多次），要求我们应答 HTTP 200 +
   {"code":"SUCCESS"}；返回 500+FAIL 时微信持续重试——配合第 3 点的幂等，重试无害。
5. **"前端轮询 queryPayStatus 和回调 notify 并发到达怎么办？"**
   要点：两条路最终都汇聚到同一个 updatePaymentStatus，条件更新保证只有一端"赢"，
   只有赢家发 MQ。notify 缺失时轮询兜底，轮询失败时回调兜底，互为冗余但不会重复。
6. **"没有商户密钥，怎么验证的？"（诚实且加分）**
   要点：分两层答——代码层：验签/金额校验/幂等逻辑全部实现，并用 6 个单元测试锁定了
   金额不一致拒绝入账、重复回调不发 MQ 等行为（mock 微信 SDK 的 Transaction 对象，
   不需要真实商户号）；集成层：因个人主体无法申请微信支付商户号，真实收款未验证，
   上线前需完成商户号配置 + 0.01 元真实支付 + 退款验证。**主动说出这个边界比被问出来好。**

## 八、存储与可观测性（简历第 5 条）

1. **"MongoDB 为什么分集合？怎么分的？"**
   要点：播放进度按 userId % 100 分到 100 个集合，控制单集合体积，避免大集合的
   索引和锁竞争退化；按用户维度查天然路由到单集合。
2. **"bitmap 怎么防刷量？"**
   要点：key=user:userId，offset=trackId，setBit 返回旧值判断是否已上报，24h 过期。
   一个用户对同一声音 24h 内只计一次播放。
3. **"traceId 链路怎么打通的？"**
   要点：网关 TraceGlobalFilter 生成 X-Request-Id → 各服务 TraceFilter 写 MDC →
   Feign 拦截器透传下游 → logback pattern 输出 %X{traceId} → Logstash 推 ES/Kibana，
   按 traceId 一键检索整条调用链；MQ 消费无 HTTP 头，各自生成独立 traceId。

## 九、场景变式题（高频，提前想好）

| 问题 | 回答思路 |
|---|---|
| 并发量翻十倍怎么办？ | 分层答：先压测定位瓶颈（不是上来就加机器）→ 缓存命中率已高则重点扩无状态服务（加实例，Nacos 自动负载）→ 瓶颈在 DB 则读写分离/分库分表 → MQ 削峰的环节扩消费者。结合本项目：搜索走 ES 可横向扩分片，交易链路数据库行锁是天然瓶颈，可按 userId 分库 |
| Redis 挂了会怎样？ | 诚实分场景：登录全挂（token 在 Redis）→ 缓存 AOP 有降级直查 DB 保读，但写锁失效 → 方案：Redis 主从+哨兵/集群，锁用 Redisson 看门狗自动续期，恢复后重建 |
| 一条支付 MQ 丢了怎么办？ | 链路本身有三层（confirm 重发、持久化、手动 ack）；极端丢失的兜底：对账——定时任务核对支付记录状态与订单状态，不一致补偿。可承认当前项目未实现对账任务，作为改进项 |
| 让你重新设计会改什么？ | 主动说 1-2 个真实弱点 + 改法：如 RabbitService 先发后存 Redis 的顺序问题、signKey 挪配置中心、SearchReceiver 的 @Retryable 无效应换手动重试。**能说出自己代码的缺点是高级信号** |
